## 먼저 고쳐야 할 부분

### 1. ZIP 이어받기에서 기존 파일을 완료분으로 오인 — 우선도 높음

`App/Receive/IPhoneUSBExportService.swift:835–884`, 복사 생략 `949–968`.

USB에 내용은 다르지만 이름·크기가 같은 파일이 있는 상태에서 덮어쓰기를 승인하고, 그 파일을 복사하기 전에 다른 파일에서 중단하면 문제가 생길 수 있다. 재개 시 대상 파일이 있고 임시 복사본이 없으면 크기만 비교해 이미 확정된 완료분으로 처리한다. 실제로 교체하지 않았는데 복사 성공·원본 삭제 가능 상태가 될 수 있다.

- 수정: 실제로 저장 확정한 항목의 기록을 사용한다. 기존 파일 존재·크기만으로 완료를 추정하지 않는다. 기록 없이 중단된 모호한 항목은 다시 처리한다.
- 유지: USB 전체 SHA 재읽기를 기본값으로 되살리지 않는다. ZIP CRC, 쓰기 오류, 크기 확인은 유지한다.
- 회귀: 기존 다른 내용/동일 크기 파일 + 덮어쓰기 승인 + 앞 파일에서 중단 + 재개 후 내용 대조. 용량 계산에서도 잘못된 완료분을 차감하지 않는지 확인한다.
- 기존 테스트: `Tests/IPhoneUSBExportServiceTests.swift`의 `testInterruptedZIPFinalizationResumesAfterOneRootItemWasAlreadyMoved`는 진짜 이전 완료분만 검사한다.

### 2. 덮어쓰기 실패 후 복구 백업이 삭제될 수 있음 — 우선도 높음

`App/Receive/IPhoneUSBExportService.swift:1069`, `App/Receive/USBZIPReceivePipeline.swift:295, 625–642`.

기존 파일의 백업 이동은 성공했지만 새 파일 설치와 백업 복구가 모두 실패하면, 복구 오류를 무시한 뒤 호출자의 무조건 백업 정리가 실행될 수 있다. 이 경우 기존 파일의 유일한 남은 사본도 지워질 수 있다. 실제 사용자 파일 손실을 확인했다는 뜻은 아니며, 해당 오류 처리 경로가 존재한다는 뜻이다.

- 수정: 커밋 성공 또는 정상 복구를 확인한 경우에만 백업을 정리한다. 복구 실패 시 백업과 복구 정보를 남기고 사용자에게 알린다.
- 회귀: 백업 이동 성공 → 새 파일 이동 실패 → 복구 이동 실패를 주입하고 기존 내용이 원래 위치나 백업 중 적어도 한 곳에 남는지 확인한다.

### 3. 여러 전송의 상태 갱신이 서로 덮어써질 수 있음 — 우선도 높음

`App/Upload/ManualBackgroundTransferEngine.swift:54–73, 420–509`.

전체 장부를 `await load()`로 읽고 수정한 뒤 `await replace()`하는 동안 다른 완료·등록 처리가 끼어들 수 있다. 각 actor 호출은 보호되지만 두 호출을 합친 읽기-수정-쓰기는 보호되지 않는다. 완료 개수, 새 작업, 분할 ETag가 이전 상태로 덮어써질 가능성이 있다.

- 수정: 작업 등록·완료·분할 완료 기록을 저장소 actor의 한 번의 동기 갱신 안에서 처리한다.
- 회귀: 두 파일 완료와 새 파일 등록을 겹쳐 완료 수, 새 작업, 분할 ETag가 모두 보존되는지 확인한다. 기존 테스트의 직렬 완료 재호출만으로는 이 경합을 검증할 수 없다.

### 4. 백그라운드 완료 처리와 시스템 종료 통지 순서 — 우선도 높음

`App/Upload/BackgroundManualUploadSession.swift:166–181`.

완료 콜백은 별도 비동기 Task에서 장부를 저장하고 다음 조각을 예약하지만, finish-events는 그 처리를 기다리지 않고 시스템 completion handler를 호출한다. 앱이 다시 정지되면 완료 기록 또는 다음 조각 예약이 미완료 상태로 남을 수 있다.

- 수정: 이미 전달된 완료 이벤트의 저장·예약 처리가 끝난 뒤 시스템 handler를 호출한다. 전체 파일 전송이 끝날 때까지 무제한으로 기다리는 방식은 아니다.
- 회귀: 완료 처리를 의도적으로 지연시킨 상태에서 finish-events가 와도 처리가 끝나기 전에는 handler가 호출되지 않는지 확인한다.
- 플랫폼 구분: 네트워크 background URLSession과 USB 로컬 복사의 실행 보장은 다르다. USB가 다른 앱 사용 중 무제한 계속된다고 안내하면 안 된다. [Apple background URLSession 문서](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background), [유한한 background task 시간](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(expirationhandler:)). HJ Search로 검색·원문 확인했다.

### 5. USB 재선택 시 이전 폴더·선택 상태 유지 — 우선도 중간

`App/UI/USBReceiverViewModel.swift:619–633, 660–678`.

이전 USB의 하위 폴더 경로와 상대 경로 선택을 새 루트에도 적용한다. 새 루트에 그 폴더가 없으면 접근 오류가 나고, 같은 경로가 있으면 다른 저장장치 파일이 이미 선택된 상태로 남을 수 있다.

- 수정: 새 루트 선택 성공 시 탐색 위치·선택·이전 목록을 초기화하고 새 루트를 조회한다. 이전 비동기 조회가 늦게 완료되어 새 목록을 덮지 않는지도 함께 검증한다.
- 회귀: 서로 다른 두 루트의 같은 이름 파일, 새 루트에 이전 하위 폴더가 없는 경우.

### 6. 시스템 설정에서 바꾼 사진 권한이 즉시 반영되지 않음 — 우선도 중간

`App/UI/ContentView.swift:164–172, 505–507`; `App/UI/ContentViewModel.swift:96–99, 118–124`.

사진 권한을 거부/제한에서 전체 허용으로 바꿔 돌아와도 앱 활성화 경로가 사진 모델을 갱신하지 않는다. 이전 권한 값으로 사진 선택을 막을 수 있다.

- 수정: foreground 복귀 시 현재 사진 권한을 갱신한다.
- 회귀: denied/limited → 시스템 설정에서 authorized → 앱 복귀 → 사진 선택 가능.

## 성능 최적화 후보

1. **업로드 진행 이벤트마다 전체 장부 재읽기 제거**
   - `App/Upload/ManualBackgroundTransferEngine.swift:103–114` → `App/Media/ManualTransferJobStore.swift:68–75`.
   - 진행 표시용 활성 상태를 메모리에서 조회하고, 실제 상태 변경만 저장한다. 진행 이벤트 병합 시 최종 이벤트는 즉시 반영한다.
   - 검증: 진행 이벤트 1,000회에 디스크 읽기가 비례해 늘지 않는지 계수하고 최종 바이트·완료 상태를 확인한다.
2. **받은 파일 목록 디스크 조회를 화면 스레드 밖으로 이동**
   - `App/UI/USBReceiverViewModel.swift:542–546, 1693–1696` → `App/Application/USBReceiverDependencies.swift:257` → `App/Receive/IPhoneReceivedFileCatalog.swift:227–261`.
   - 전체 폴더 조회·파일 속성 조회·정렬이 현재 MainActor 경로에 있다. 조회 결과만 UI에 적용하고 연속 완료 이벤트의 조회를 합친다.
   - 검증: 느린 조회 중 화면 응답성, 다수 파일 수신 후 목록 누락, 오래된 조회 결과의 역전 적용 여부.

두 항목 모두 속도 향상 배수나 초 단위 효과는 실측하지 않았다. USB 매체·리더기 속도가 빨라진다는 보장이 아니라 불필요한 앱 작업과 화면 지연을 줄이는 최적화다. 큰 파일을 통째로 메모리에 올리는 방식은 사용하지 않는다.

## 추가 기능 추천 — 아직 구현하지 않음

| 우선 | 기능 | 용도 및 제약 |
| --- | --- | --- |
| 1 | 수동 전송 기록 및 실패 파일만 재전송 | 전체를 다시 선택하지 않고 실패 파일명·수신처·사유를 보고 재시도. 일반 파일의 권한이 만료되면 재선택 필요. 현재 자동 사진 재시도와는 별개다. |
| 2 | 받은 사진·PDF·ZIP 여러 개 공유 | 현재 공유창의 단일 URL을 다중 선택으로 확장. 실제 첨부 허용 개수·형식은 카카오톡 등 공유 대상이 결정한다. |
| 3 | ZIP 내부 목록과 선택 압축 해제 | 큰 ZIP을 전부 풀지 않고 필요한 파일·폴더만 선택. 기존 루트 배치와 충돌 확인 정책 유지. |

| 5 | 오류 진단 내보내기 | 앱 버전·단계·오류 코드·처리 개수만 모아 공유. 인증값·수신코드·개인 파일 경로는 제외. |

받은 파일 이름 검색/종류 필터, 단일 사진·PDF·ZIP 공유, 공간 부족 사전 확인, 선택형 수신·USB 결과 알림은 이미 있으므로 신규 기능으로 중복 제안하지 않는다.
