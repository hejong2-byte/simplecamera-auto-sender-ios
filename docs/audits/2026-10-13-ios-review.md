## 우선 수정할 결함

### R1. [P1] 일반 파일의 마지막 교체 시 덮어쓰기 승인 재확인 누락

- 근거: `App/Receive/IPhoneUSBExportService.swift:575-579,598,696-708`.
- 시작 시 동명 파일이 없더라도, 파일 조정 작업 진입 전 다른 작업이 같은 이름의 파일을 만들 수 있다. 마지막 커밋은 대상 존재만 보고 교체하며 `overwriteExisting` 승인을 다시 확인하지 않는다.
- 영향: 승인하지 않은 USB 파일이 교체될 수 있다. 직접 수신 경로는 `USBReceiveService.swift:631-638`에서 마지막 검사를 이미 한다.
- 최소 수정: 일반 파일 내보내기도 마지막 커밋에서 충돌과 승인을 재확인하고, 미승인이면 원본을 보존한 채 확인창으로 돌아간다.
- 회귀 조건: `coordinateWrite` 두 번째 호출 직전에 동명 파일 생성 → 승인 없이 교체하지 않음. 현재 일반 파일 충돌 테스트는 처음부터 존재한 파일만 다룬다.

### R2. [P2] USB 직접 ZIP 수신 재개가 기존 이어받기 식별자를 바꿈

- 근거: `App/Receive/USBReceiveService.swift:717-726,749-790`; `App/Receive/USBReceiveLedger.swift:73-80`; `App/Receive/IPhoneUSBExportService.swift:760-775,1549-1568`.
- ZIP 다운로드·검증을 마친 뒤 USB 복사 중 중단해도, 다음 시도에서 ZIP을 청크 경계까지 자르고 꼬리 부분을 다시 받는다. 청크 크기의 배수가 아닌 ZIP은 실제 내용 재쓰기가 발생한다.
- 영향: 원본 수정시각이 바뀌는데 내보내기 재개 식별자에 이 시각이 포함된다. 이전 압축 해제 결과·USB 부분 복사본을 못 찾고 새 작업을 시작할 수 있다. 이전 임시파일도 남을 수 있다.
- 최소 수정: 검증 완료한 ZIP과 다운로드 미완료 ZIP의 상태를 구분한다. 완료 원본은 변경하지 않고 동일한 공유 내보내기 작업으로 재개한다. 원본 변경 검사를 통째로 없애는 해결은 피한다.
- 회귀 조건: `USBReceiveService.runOnce → USB 복사 도중 중단 → runOnce` 통합 경로에서 다운로드 꼬리 재요청·재압축 해제 없이 기존 작업 재사용. 현재 내보내기 단독 재개 시험만으로는 이 경계를 검증하지 못한다.

### R3. [P2] 일시 수신 실패 후 같은 파일을 다시 선택해도 진행되지 않음

- 근거: `App/Receive/IPhoneLocalReceiveEngine.swift:152-156,199-228,264-266,441-448`; `App/Application/USBReceiverDependencies.swift:385-390`.
- 연결 끊김·시간초과·취소까지 모두 `.failed`에 저장한다. 발견 단계는 실패 작업을 포함한 모든 기존 ID를 제외하며, 복구 단계는 `.failed`를 재설정하지 않는다.
- 화면 정책은 실패 파일의 재선택을 허용하지만 재승인은 승인 기록만 변경한다. 따라서 목록에서 영구적으로 사라지는 문제가 아니라, 재선택해도 수신 엔진이 시작하지 않는 문제다.
- 최소 수정: 일시 오류/사용자 중단과 무결성 실패를 구분하고 명시적 재수신 경로를 제공한다. SHA 불일치 파일을 자동 성공 처리하지 않는다.
- 회귀 조건: 네트워크 실패 → 재승인 → 같은 delivery 재수신 성공. 기존 SHA 실패 비재시도 테스트는 별도로 유지한다.

### R4. [P2] 서버 완료 확인(ACK) 실패 뒤 화면을 열어둬도 재시도되지 않음

- 근거: `App/Receive/IPhoneLocalReceiveEngine.swift:120-122,202-204,407-413`; `App/UI/USBReceiverViewModel.swift:984-998`; `App/Application/USBReceiverDependencies.swift:224-225`.
- ACK 실패는 `.ackPending`으로 저장하지만 정기 확인은 `discoverAndSchedule`만 호출한다. 해당 함수는 `.ackPending`이 있으면 바로 반환한다. ACK 복구는 초기화 또는 백그라운드 세션 재기동 시의 `restore` 경로에만 있다.
- 영향: 네트워크가 회복돼도 서버 확인 대기가 지속되고 후속 파일 수신까지 막힐 수 있다.
- 최소 수정: 화면의 정기 확인에서도 기존 작업 복구를 먼저 직렬 실행한다. ACK 재시도 때문에 이미 받은 파일을 다시 받거나 사진에 중복 저장하지 않는다.
- 회귀 조건: 첫 ACK 실패 → 앱을 계속 활성 상태로 유지 → 정기 확인만으로 ACK 및 다음 수신 진행. 기존 시험은 `restore()`를 직접 호출한다.

### R5. [P2] 백그라운드 수신 처리보다 시스템 완료 통지가 먼저 나갈 수 있음

- 근거: `App/Receive/BackgroundIPhoneReceiveSession.swift:177-189,208-218`.
- 다운로드 완료 파일은 staging으로 옮기지만 이후 장부·최종 저장은 별도 `Task`다. 시스템 완료 handler는 그 Task의 durable 처리를 기다리지 않는다.
- 영향: 장부 갱신 전에 앱이 정지·종료되는 경우 staging 파일과 작업 상태가 불일치할 수 있다. 재다운로드 후 `stagingFileExists` 오류로 이어질 가능성이 있다. 이 실기기 발생 빈도는 미측정이다.
- 최소 수정: 수동 업로드 세션처럼 이미 전달된 완료/실패 callback 작업을 추적하고, durable 처리 후 시스템 완료 handler를 호출한다. 미래의 모든 전송이 끝날 때까지 무한 대기시키지는 않는다.
- 회귀 조건: 완료 callback을 지연시킨 상태에서 finish-events 호출 → 저장 전 handler 미호출. staging 이동과 장부 저장 사이의 종료 복구도 확인한다.
- 현재 수신 세션 시험은 descriptor·registry·identifier 3개뿐이며 callback drain 시험이 없다.

### R6. [P2] 일반 파일 덮어쓰기 복구 실패 시 백업 위치가 안내되지 않음

- 근거: `App/Receive/IPhoneUSBExportService.swift:1267-1272`; `App/Receive/USBReceiveService.swift:1182-1187`.
- 기존 파일 백업 후 새 파일 설치와 복원까지 실패하면 복원 오류를 `try?`로 버린다.
- 영향: 원본 백업은 숨김 폴더의 무작위 `.backup` 이름으로 남지만, 원래 경로에는 파일이 없고 사용자에게 복구 위치가 표시되지 않는다. 백업이 자동 삭제된다는 주장은 아니다.
- 최소 수정: ZIP 경로에서 이미 사용하는 복구 오류·백업 위치 전달 방식을 일반 파일 경로에도 적용한다.
- 회귀 조건: 일반 파일 설치 실패 + rollback 실패 → 원본 백업 보존 및 복구 경로 표시. 현재 이중 실패 시험은 ZIP 경로 중심이다.

### R7. [P2] 텍스트 전송 중 작성한 다음 초안이 지워짐

- 근거: `App/UI/TextTransferViewModel.swift:167-173`; `App/UI/TextTransferView.swift:114-119,143-150`.
- 수신코드/본문은 전송 중에도 편집 가능하지만, 이전 메시지의 전송 완료 후 현재 본문을 무조건 비우고 빈 초안을 저장한다.
- 최소 수정: 전송 시점 이후 초안이 변경되지 않았을 때만 비운다. 또는 전송 중 편집 잠금을 명확히 제공한다.
- 회귀 조건: 전송 응답 지연 → 다음 본문 입력 → 첫 전송 완료 후 다음 초안 보존. 기존 busy 시험에는 전송 중 편집 조건이 없다.

### R8. [P2] USB 파일 연속 전송에서 두 번째 선택이 접수 없이 사라짐

- 근거: `App/UI/USBStorageManagementView.swift:187,284-289,354-363`; `App/UI/ContentViewModel.swift:232-234`; `App/UI/USBReceiverViewModel.swift:938-944`.
- 첫 파일의 백그라운드 업로드가 진행 중이어도 USB 탐색 화면의 busy 조건에는 공통 수동 전송 상태가 없다. 두 번째 전송은 실제 전송 모델의 busy guard에서 조용히 반환된다.
- 탐색 모델은 `Void` 콜백 반환을 접수 성공처럼 처리해 선택을 지운다. 두 번째 파일은 큐에 들어가지 않는다.
- 최소 수정: 공통 busy 상태를 반영하고 enqueue 접수 결과가 성공일 때만 선택 해제한다. 대기열 지원 여부는 별도 명확히 결정한다.
- 회귀 조건: 실제 ContentViewModel을 연결해 첫 전송 진행 중 두 번째 선택·전송. 선택 보존/명확한 대기 안내 또는 실제 큐 접수를 확인한다.

## 최적화 우선순위

### O1. USB 직접 일반 파일 수신의 중복 전체 SHA 읽기 제거 검토

- `USBReceiveService.swift:586-588,624-625`에서 다운로드 중 SHA를 계산했지만, `663 → 1080-1090 → 1098-1116`에서 최종 USB 파일을 다시 전부 읽는다.
- 해당 추가 읽기는 진행 callback도 넘기지 않는다. 대용량 파일의 완료 대기 원인이 될 수 있다.
- 서버 수신 SHA·쓰기/닫기 오류·파일 크기 확인은 유지하고, 추가 전체 읽기만 사용자 선택 정밀 검증으로 분리한다. ZIP 압축 손상 CRC는 유지한다.
- 이는 iPhone 저장 파일을 USB로 내보내는 경로와 다른 남은 경로다. 현재 시험은 직접 수신의 재검증을 제거하도록 검증하지 않는다.

### O2. ZIP 목록의 선택 해제 O(N²) 작업

- `USBReceiverViewModel.swift:599,607-617`: 전체 선택 상태에서 하나를 해제하면 선택 경로마다 전체 ZIP 항목을 다시 찾는다. MainActor의 동기 처리다.
- 일반 파일 1만 개의 평면 ZIP은 약 1억 번 비교가 필요할 수 있다. 이는 비교 횟수 분석이며 실제 지연 시간 측정은 아니다.
- 디렉터리 집합을 미리 만들고 해당 항목의 조상 경로만 해제하면 중첩 전체 탐색을 없앨 수 있다. 폴더/하위 파일 선택 의미는 보존한다.
- 기능 시험에 더해 1천/1만 항목 규모 시험이 필요하다.

### O3. 수신 진행률마다 전체 작업 JSON 재저장

- `IPhoneLocalReceiveEngine.swift:236-242`는 progress마다 job 저장을 호출한다. `IPhoneLocalReceiveJobStore.swift:57-67,80-85`는 전체 작업 목록을 정렬·인코딩해 atomic write한다.
- 완료 작업도 목록에 쌓이므로 장기간 사용 시 매 이벤트 비용이 커진다.
- 진행 바이트는 메모리에서 갱신하고 일정 간격의 checkpoint로 합치되, 단계 변경·완료·실패는 즉시 저장한다. 재시작 복구에 필요한 상태를 먼저 정의해야 한다.

## 추가할 만한 기능

1. **설정에 현재 버전/빌드와 업데이트 확인**: 현재 앱 소스에서 버전 표시·최신 릴리스 비교 기능을 찾지 못했다. 기존 설치 QR/SideStore 경로로 연결하고 업데이트가 곧 설치 완료라는 표시를 하지 않는다.
2. **오류 진단 내보내기**: 작업 종류, 단계, 오류 코드, 앱 버전, 마지막 정상 checkpoint를 사용자 선택으로 공유한다. 인증값·수신 비밀값·본문은 제외하고 파일명/경로 포함 여부도 명시한다. 현재 범용 진단 보고서 생성·공유 기능은 확인되지 않는다.

## 권장 진행 순서

1. R1/R6 원본 보호와 덮어쓰기 승인.
2. R2~R5 수신·이어받기·백그라운드 복구 통합 회귀.

4. O1~O3 성능 개선. 무결성 검사를 일괄 삭제하지 않는다.
5. 버전 확인/진단 내보내기 등 추가 기능은 안정화 이후 별도 변경으로 적용.
