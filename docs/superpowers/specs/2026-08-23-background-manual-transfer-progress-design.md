# 수동 미디어 백그라운드 전송·진행률 설계

## 확인된 문제

2026-08-23 실제 iPhone 전송을 Cloudflare Worker 실시간 로그로 재현했다.

- 멀티파트 시작 요청은 성공했다.
- 동영상 조각 업로드는 모두 HTTP 200을 받았다.
- 최종 조립 요청은 HTTP 422를 받았다.
- 앱은 이어서 멀티파트 중단 요청을 보냈고 HTTP 204를 받았다.
- PC 수신 DB와 저장 폴더에는 동영상이 도달하지 않았다.

현재 Worker는 최종 조립 뒤 `메타데이터 누락`, `ID 불일치`, `전체 크기 불일치`를 하나의 422 응답으로 처리한다. 따라서 어느 조건이 실패했는지 앱에서 구분할 수 없다. iPhone 앱도 수동 묶음 전체가 끝난 뒤에만 요약을 게시하므로, 긴 동영상이 실패해도 전송 도중 실패 수가 즉시 증가하지 않는다. 수동 전송은 기본 `URLSession`을 사용하므로 앱이 백그라운드에서 정지되면 장시간 업로드의 계속 실행을 보장하지 못한다.

## 목표와 성공 기준

수동으로 선택한 사진·스크린샷·동영상을 실제 바이트 진행률과 함께 전송하고, 사용자가 Safari·YouTube 등 다른 앱을 사용하거나 화면을 잠근 동안에도 iOS가 전송을 이어가게 한다.

성공 기준은 다음과 같다.

1. 수동 전송 상태에 현재 단계, 현재 파일 순서, 프로그래스바, 정수 퍼센트, 전송 바이트, 완료·실패·전체 수가 표시된다.
2. 완료·실패 수는 파일 하나가 끝날 때마다 즉시 갱신된다.
3. 앱 전환, 화면 잠금 또는 시스템에 의한 앱 프로세스 종료 뒤에도 예약된 파일 업로드가 계속되거나 같은 세션 식별자로 복원된다.
4. 사용자가 멀티태스킹 화면에서 앱을 강제 종료한 경우에는 iOS 제약을 그대로 알리고, 다음 앱 실행 때 미완료 작업을 재개한다.
5. 약 300~400MB MOV·MP4를 포함해 2GiB 이하 파일의 멀티파트 조립과 서버 무결성 검증이 성공한다.
6. 최종 검증 실패 시 실패 조건과 HTTP 상태가 사용자에게 표시되고 실패 수가 증가한다.
7. 기존 Simple Cam 자동 전송, 선택하지 않은 사진 차단, Keychain 인증과 PC 무결성 검증은 바뀌지 않는다.

## 범위와 제외 사항

이번 변경은 iPhone의 수동 미디어 전송, Cloudflare Worker의 멀티파트 완료 검증, 관련 상태 UI에 한정한다.

- 기존 Simple Cam 닫기 자동화와 자동 사진 POST 경로는 변경하지 않는다.
- PC 수신기의 저장·검증·썸네일 구조는 이미 MOV·MP4를 지원하므로 프로토콜 변경이 없는 한 수정하지 않는다.
- 앱이 스스로 종료되거나 다른 앱을 자동으로 여는 동작은 구현하지 않는다. iOS에서 사용자가 홈 화면으로 이동하거나 다른 앱으로 전환하는 동안 전송을 지속하는 것이 목표다.
- 멀티태스킹 화면에서 사용자가 앱을 강제 종료한 뒤에도 전송이 계속된다고 표시하지 않는다.
- R2 S3 자격 증명이나 업로드 토큰을 앱 파일·상태 DB·로그에 저장하지 않는다.

## 사용자 화면

메인 화면의 `수동 전송 상태` 카드는 다음 상태를 표시한다.

### 대기

- `전송할 종류를 선택하세요.`
- 프로그래스바는 숨긴다.
- 직전 묶음의 선택·완료·실패 수는 유지한다.

### 원본 준비

- `동영상 1/3 · 원본 준비 중`
- 아직 전체 바이트를 모르는 동안에는 회전형 진행 표시를 사용한다.
- 선택·완료·실패 수를 함께 표시한다.

### 업로드

- `동영상 1/3 전송 중`
- 현재 파일 기준 프로그래스바와 `67%`를 표시한다.
- `128MB / 192MB`처럼 성공 확정 조각과 현재 전송 조각의 바이트를 표시한다.
- 여러 파일의 크기가 크게 다르므로 퍼센트는 현재 파일 기준으로 삼고, 묶음 전체는 `완료 1 · 실패 0 · 전체 3`으로 표시해 의미를 섞지 않는다.

### 재시도와 서버 검증

- 조각 재시도 시 `네트워크 재시도 2/3`과 성공 확정 지점부터의 진행률을 표시한다.
- 마지막 조각 뒤에는 `서버에서 파일 검증 중`을 표시한다.
- 재시도 때문에 이미 보낸 바이트를 다시 보내는 경우, 퍼센트는 성공 확정 바이트 위치로 돌아갈 수 있으며 재시도 문구로 이유를 알린다.

### 완료와 실패

- 성공: `동영상 전송 완료 · 완료 3 · 실패 0`
- 실패: `동영상 전송 실패 · 서버 크기 검증 실패 (HTTP 422)`
- 실패한 파일이 확정되는 즉시 실패 수를 증가시킨다.
- 미완료 묶음이 있으면 앱 재실행 후 같은 단계와 수를 복원한다.

## iPhone 구조

### 전송 상태 모델

`ManualTransferProgress`는 UI와 전송 엔진 사이의 단일 상태 모델이다.

- 묶음 ID와 미디어 종류
- 선택 수, 현재 파일 순서, 완료 수, 실패 수
- 현재 단계: 준비, 업로드 시작, 조각 업로드, 재시도, 서버 검증, 완료, 실패
- 현재 파일의 전체 바이트, 성공 확정 바이트, 현재 작업 전송 바이트
- 안전하게 정규화된 사용자 오류 코드와 HTTP 상태

퍼센트는 `성공 확정 바이트 + 현재 작업에서 전송한 바이트`를 현재 파일 전체 바이트로 나누고 0~100으로 제한해 계산한다. 상태 계산은 UI와 분리한 순수 로직으로 두어 단위 테스트한다.

### 영속 작업 장부

`ManualTransferJobStore`를 앱 지원 디렉터리에 두고 원자적으로 저장한다.

- 선택한 PhotoKit 로컬 식별자만 기록한다.
- 내보낸 임시 파일 경로, 원본 이름·MIME·촬영시각, 크기·SHA-256을 기록한다.
- R2 업로드 ID, 완료된 조각 번호·ETag, 현재 재시도 횟수와 작업 상태를 기록한다.
- 인증값과 사진·동영상 내용은 JSON 장부에 넣지 않는다.
- 성공한 파일의 임시 원본과 조각만 삭제한다. 실패·중단 작업은 재개 여부가 결정될 때까지 필요한 파일을 보존한다.

### 백그라운드 세션

수동 업로드 전용 `URLSessionConfiguration.background(withIdentifier:)` 세션 하나를 사용한다.

- `sessionSendsLaunchEvents = true`로 완료 이벤트를 앱에 전달한다.
- 즉시 전송이 목적이므로 `isDiscretionary = false`로 둔다.
- 모든 요청 본문은 파일 기반 `URLSessionUploadTask`로 예약한다.
- 세션 delegate의 `didSendBodyData`로 현재 작업의 실제 전송량을 상태 모델에 반영한다.
- 앱 실행 시 같은 세션 식별자로 작업을 다시 연결하고, 시스템 작업 목록과 영속 장부를 대조한다.
- 작업 설명에는 비밀값 대신 묶음 ID·파일 순서·조각 번호만 넣는다.

백그라운드 세션은 앱이 정지되거나 시스템에 의해 종료돼도 별도 프로세스에서 파일 전송을 수행할 수 있다. 사용자가 앱을 강제 종료하면 iOS가 백그라운드 작업을 취소하므로, 다음 실행 때 장부를 읽어 마지막 성공 조각 이후부터 새 작업으로 재개한다.

### 멀티파트 흐름

1. 선택한 자산 하나를 원본 임시 파일로 내보낸다.
2. 스트리밍 SHA-256과 실제 파일 크기를 계산하고 작업 장부에 기록한다.
3. 95MiB 이하 파일은 한 개의 백그라운드 파일 업로드 작업으로 예약한다.
4. 큰 파일은 멀티파트 시작 요청을 파일 기반 작업으로 예약한다.
5. 시작 응답의 업로드 ID를 저장한 뒤 32MiB 조각 파일을 만든다. 마지막 조각을 제외한 조각은 정확히 같은 크기가 되도록 파일 읽기를 반복해 채운다.
6. 최대 세 개의 조각을 동시에 백그라운드 업로드하고, 성공한 조각 번호·ETag를 즉시 저장한다.
7. 모든 조각 성공 뒤 완료 JSON을 파일로 만들고 백그라운드 POST 작업으로 예약한다.
8. 서버 검증 성공 응답을 받은 뒤에만 앱 장부를 완료로 바꾸고 임시 파일을 삭제한다.

같은 파일을 재개할 때 이미 성공한 조각은 다시 보내지 않는다. 서버가 업로드 ID를 더 이상 인정하지 않을 때만 새 멀티파트를 시작한다.

## 재시도와 실패 분류

- `URLError`의 일시적 연결 오류와 HTTP 408·425·429·5xx는 해당 요청만 최대 3회 재시도한다.
- 재시도 간격은 1초, 3초, 9초이며 성공한 다른 조각은 보존한다.
- HTTP 401·403은 인증 실패로 즉시 중단하고 인증 설정 안내를 표시한다.
- 형식 오류와 다른 영구 4xx는 자동 재시도하지 않는다.
- 최종 서버 검증 실패는 `metadata_missing`, `id_mismatch`, `size_mismatch`로 구분한다.
- 재시도 소진 뒤 실패가 확정되면 해당 파일의 실패 수를 즉시 증가시키고 다음 선택 파일을 계속 처리한다.
- 영구 실패나 재시도 소진 시 활성 멀티파트를 중단해 서버 임시 조각을 정리한다. 앱 강제 종료처럼 다음 실행에서 재개할 수 있는 중단에는 서버 abort를 보내지 않는다.

## Worker 완료 검증 수정

Worker는 `R2MultipartUpload.complete()` 반환값만으로 세 조건을 한 번에 판단하지 않는다.

1. 조립을 완료한다.
2. R2의 강한 일관성을 이용해 같은 객체 키를 `head()`로 다시 조회한다.
3. 객체 존재, custom metadata 존재, ID 일치, 선언 크기와 실제 객체 크기 일치를 각각 검사한다.
4. 실패 응답에는 비밀이나 파일명을 넣지 않고 안정적인 오류 코드와 HTTP 422만 반환한다.
5. 검증 실패 객체는 삭제하고, 서버 로그에는 오류 코드와 선언·실제 크기 같은 비민감 숫자만 남긴다.
6. 성공 시 기존 PC 목록 API가 읽는 custom metadata를 그대로 유지한다.

조각 업로드에서는 `X-Part-Size`, 실제 `Content-Length`와 R2가 반환한 조각 결과를 검증한다. 완료 요청의 조각 번호는 중복 없이 오름차순이어야 하며, 마지막 조각을 제외한 조각 크기는 동일하게 생성한다.

## 데이터 보호

- 수동 전송은 시스템 선택기가 돌려준 식별자만 처리하며 사진 보관함 전체를 스캔하지 않는다.
- 원본 파일, 위치, 인증 헤더, R2 업로드 ID는 사용자 메시지나 일반 로그에 출력하지 않는다.
- 작업 장부는 기존 자동 전송 장부와 별도 파일을 사용해 자동 사진 상태를 오염시키지 않는다.
- 서버가 성공을 확인하기 전에는 PC 수신 완료나 앱 전송 완료로 세지 않는다.
- PC는 기존처럼 전체 파일 크기, SHA-256과 MOV·MP4 서명을 확인한 뒤 저장·ACK한다.

## 검증 계획

구현은 테스트 우선으로 진행한다.

### iOS 단위 테스트

- 실제 바이트 진행률과 0~100 제한
- 파일 완료·실패 직후 묶음 수 갱신
- 재시도 시 성공 확정 바이트 보존
- HTTP 상태와 사용자 오류 문구 매핑
- 영속 작업 장부 저장·복원과 비밀값 미포함
- 앱 재실행 시 세션 작업과 장부 재연결
- 정확한 32MiB 조각과 작은 마지막 조각 생성
- 성공한 조각 건너뛰기와 재시도 소진 처리

### Worker 테스트

- 멀티파트 완료 뒤 `head()` 결과로 성공 검증
- metadata 누락, ID 불일치, 크기 불일치를 서로 다른 오류 코드로 반환
- 검증 실패 객체 삭제
- 기존 자동 사진 POST와 수동 단일 PUT 회귀 없음

### 통합 검증

- iPhone에서 100MB 미만 파일과 약 300~400MB MOV·MP4 전송
- 업로드 중 Safari·YouTube 전환 및 화면 잠금
- 앱을 다시 열었을 때 진행률·완료·실패 상태 복원
- 네트워크 일시 중단 뒤 조각 재시도와 중복 없는 PC 저장
- PC 수신 파일의 크기·SHA-256 검증과 ACK 확인

## 배포

앱 버전은 `0.1.8`, 빌드는 `6`으로 올린다. iOS 전체 CI, Worker 테스트와 실제 약 300MB 동영상 전송을 통과한 뒤 Worker를 먼저 배포하고 SideStore IPA와 QR을 게시한다. Worker 배포 전에는 새 앱을 공개하지 않아 프로토콜 버전 불일치를 피한다.
